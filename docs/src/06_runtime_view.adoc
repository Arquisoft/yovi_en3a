== Runtime View
This section illustrates key runtime operations and interactions among the system’s components.

ifdef::arc42help[]
[role="arc42help"]
****
.Contents
The runtime view describes concrete behavior and interactions of the system’s building blocks in form of scenarios from the following areas:

* important use cases or features: how do building blocks execute them?
* interactions at critical external interfaces: how do building blocks cooperate with users and neighboring systems?
* operation and administration: launch, start-up, stop
* error and exception scenarios

Remark: The main criterion for the choice of possible scenarios (sequences, workflows) is their *architectural relevance*. It is *not* important to describe a large number of scenarios. You should rather document a representative selection.

.Motivation
You should understand how (instances of) building blocks of your system perform their job and communicate at runtime.
You will mainly capture scenarios in your documentation to communicate your architecture to stakeholders that are less willing or able to read and understand the static models (building block view, deployment view).

.Form
There are many notations for describing scenarios, e.g.

* numbered list of steps (in natural language)
* activity diagrams or flow charts
* sequence diagrams
* BPMN or EPCs (event process chains)
* state machines
* ...


.Further Information

See https://docs.arc42.org/section-6/[Runtime View] in the arc42 documentation.

****
endif::arc42help[]

=== User registration

This scenario shows how a user registers in the system, including how the frontend and backend communicate.

[plantuml,"Sequence diagram - Register",png]
----
hide footbox

actor User
participant "Webapp" as Webapp
participant "Gateway Service" as Gateway
participant "Users Service" as Service

User -> Webapp : Fill registration form\n{ username, email, password }
Webapp -> Gateway : POST /api/users/register
Gateway -> Service : POST /register\n{ username, email, password }
Service --> Service : Validate input\nHash password (bcrypt)\nStore in MongoDB

alt Success
    Service --> Gateway : { message: "User created" }
    Gateway --> Webapp : Forward response
    Webapp -> User : Show welcome message\nRedirect to login
else Error
    Service --> Gateway : { error: "User already exists" }
    Gateway --> Webapp : Forward response
    Webapp -> User : Show error message
end
----

=== User Login

This scenario shows how a user logs into the system, including how the frontend and backend communicate.

[plantuml,"Sequence diagram - Login",png]
----
hide footbox

actor User
participant "Webapp" as Webapp
participant "Gateway Service" as Gateway
participant "Users Service" as Service

User -> Webapp : Fill login form\n{ username, password }
Webapp -> Gateway : POST /api/users/login
Gateway -> Service : POST /login\n{ username, password }
Service --> Service : Validate credentials\nCompare password (bcrypt)

alt Success
    Service --> Gateway : { token: JWT, userId }
    Gateway --> Webapp : Forward response
    Webapp -> Webapp : Store JWT in session
    Webapp -> User : Redirect to main menu
else Error
    Service --> Gateway : { error: "Invalid credentials" }
    Gateway --> Webapp : Forward response
    Webapp -> User : Show error message
end
----



=== Game loop

This scenario shows how a user plays a game, including interactions with the web app, game core, and bot service.

[plantuml,"Sequence diagram - Game Loop ",png]
----

actor "Player" as User
participant "WebApp" as Web
participant "Gateway Service" as Gateway
participant "Game Manager" as GameCore
participant "Gamey Engine" as Bot

User -> Web : Start Game\nSelect difficulty & board size
Web -> Gateway : POST /api/game-manager/create/standard\n{ botId, boardSize }
Gateway -> GameCore : POST /create/standard\n{ botId, boardSize }
GameCore -> GameCore : Create game\nStore in MongoDB
GameCore --> Gateway : { gameId, yen, status }
Gateway --> Web : { gameId, yen, status }
Web --> User : Game started

loop until game over

    User -> Web : make move\n{ x, y, z }
    Web -> Gateway : POST /api/game-manager/game/:id/move\n{ coords }
    Gateway -> GameCore : POST /game/:id/move\n{ coords }
    GameCore -> GameCore : apply player move\ncheck if game over

    GameCore -> Bot : POST /v1/ybot/choose/{botId}\n{ yen }
    Bot --> GameCore : { coords }
    GameCore -> GameCore : apply bot move\ncheck if game over

    GameCore --> Gateway : { yen, status }
    Gateway --> Web : { yen, status }
    Web --> User : show updated board

end

Web --> User : Game Over

----
